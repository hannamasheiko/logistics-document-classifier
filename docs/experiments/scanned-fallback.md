# OCR + visual fallback feasibility experiment (Task 5 / G2)

## Status

Feasibility experiment complete; not yet integrated with Django/production code. All fixture generation, OCR, and visual-model calls live in `experiments/scanned_fallback.py` and are independent of `documents/`. Production integration is Task 6 and requires a separate go-ahead from the user; closing this G2 write-up does not by itself start Task 6.

## Tool choices

- **Rendering:** `pypdfium2`, already vetted during Task 1 G1 preparation (renders both inspected pages correctly there, while Poppler failed with a Fontconfig error). Pure Python wheel, no system dependency, permissive license. Considered PyMuPDF as an alternative (richer API) but rejected it for this project: AGPL-3.0 licensing versus pypdfium2's permissive license, with no concrete capability gap identified to justify the trade-off.
- **OCR:** `pytesseract` over the system `tesseract` binary (installed locally via Homebrew, English + orientation/script-detection data only). Chosen as the most common free local OCR engine; no comparison against alternative OCR engines was performed, per the plan's explicit scope (pick one, do not benchmark candidates).
- **Visual fallback model:** the same `gpt-5.4-mini-2026-03-17` already frozen for primary text classification. Confirmed via the official model page that it accepts image input at the same published price ($0.75/M input, $4.50/M output tokens); no separate vision-capable model was evaluated since this one already met the need.

## Text-sufficiency / page policy

Developed and revised through direct review with the user; the process itself is part of the record because the first proposal did not survive contact with a concrete test.

1. **Initial proposal (rejected on testing):** treat native `pypdf` text under a fixed length (e.g. 20 non-whitespace characters) as "insufficient, needs OCR." Built the `scan-stray-text-over-image-bol-rail.pdf` fixture specifically to test this: a scanned page with a realistic date/reference stamp added as real vector text (`"Scanned: 2026-09-07  Ref: 88214"`, 27 non-whitespace characters) over an otherwise image-only page. This exceeded the proposed 20-character threshold, so the naive rule would have wrongly treated the page as "has usable native text" and skipped OCR, discarding the substantive content that exists only in the image. The threshold-based approach was abandoned specifically because of this test, not preemptively.
2. **Adopted policy:** since local OCR is free (no per-call API cost, only CPU time), always render and OCR every page in addition to native extraction. Compare non-whitespace character counts; use OCR text only when it is *strictly longer* than native text, otherwise keep native text. This is self-calibrating per document instead of relying on a fixed guess.
3. **Verification of the adopted policy** (`extract_effective_text` in `experiments/scanned_fallback.py`):
   - Clean real text-layer pages: native and OCR-of-rendered-page character counts were *exactly equal* on all three checked (317/317, 163/163, 227/227) — no regression risk of preferring noisier OCR over exact native text.
   - Fully image-only pages: native = 0, OCR = 250–410 → OCR correctly selected.
   - Stray-text boundary case: native = 27, OCR = 344 → OCR correctly selected, recovering the real content instead of the stray stamp.
   - Poor-quality scan: native = 0, OCR = 100 (garbage) → OCR is still the only available source; its low quality is handled downstream by evidence-based routing, not at this stage.
4. **Mixed pages:** the same per-page rule applies independently to every page; no separate mixed-page mechanism is needed. Not empirically tested beyond single-page fixtures — this is a design decision, not a verified behavior, and is listed under limitations.
5. **Unrenderable pages (agreed with the user):** if a page cannot be rendered at all, that remains a technical `FAILED` outcome (existing category), not a silent skip or an automatic `UNCERTAIN`/`OTHER`. Not exercised by a fixture in this experiment.
6. **Explicitly out of scope:** detecting a *garbled but non-short* native text layer (e.g. corrupted font encoding producing readable-length but meaningless text) is a different, harder heuristic problem not addressed here.

### Insufficient-content override (the reason this check exists)

On `scan-poor-quality-bol-rail.pdf`, local OCR produced unreadable garbage ("mame le ...", ~100 characters). Without any new mechanism, the model still assembled a *complete* critical-feature combination from that garbage and would have been accepted under a candidate class (`OTHER`) that does not match the document's actual class (`BOL`) — a genuine false-accept risk, not a hypothetical one. The already-existing (but previously advisory-only) `insufficient_readable_content` diagnostic was present in that same response. Promoting it to a deterministic override — checked before the combination rules, for non-native-text sources only — correctly forced `ESCALATE` instead.

This was a considered choice among options discussed with the user: not silently accepting the risk, not inventing a new statistical OCR-confidence threshold (rejected as inconsistent with the project's established evidence-based-only philosophy), and not rejecting the upload outright before ever trying the visual fallback (rejected because that would discard exactly the case the visual fallback exists to rescue, and would itself need the same kind of ad hoc quality heuristic to decide "reject now"). The chosen option reuses an evidence field the model already produces, rather than adding a new confidence mechanism.

## Visual fallback

### Design

- **Model:** the same `gpt-5.4-mini-2026-03-17`, given the rendered page image instead of text, via the Responses API `input_image` content part (`detail: "high"`).
- **Feature/diagnostic set:** intentionally identical to the primary text contract (same IDs and descriptions), per explicit user decision: the class definitions do not change with input modality, and a vision-capable model can still read printed text in the image, so a reduced feature set would only lose signal without any offsetting benefit. No visual-only features (e.g. logos, physical signatures, stamps) were added either, for lack of a concrete identified need.
- **Evidence:** a short free-text description of what was seen and roughly where on the page, explicitly *not* a machine-checkable exact quote — there is no source string to verify an image excerpt against. This is a real, documented reduction in verifiability compared to primary text evidence, not something to present as equivalent.
- **Acceptance:** reuses the same critical-combination routing function (`documents.services.routing.evaluate_routing`) plus the same insufficient-content override, applied independently and validated on visual examples below rather than assumed from the primary/OCR results.

### Live results

Two runs, 3 then 4 calls (severely-degraded case added after reviewing the first three), 7 calls total, no retries, ~$0.0516 combined with the OCR-sourced run above.

| Case | Source | Candidate | Action | Reason | Note |
|---|---|---|---|---|---|
| `clean-text-layer-baseline` | `v2-heldout-bol-rail.pdf` rendered to image | BOL | ACCEPT | complete_candidate_combination | sanity check on an easy, clear image |
| `incomplete-fragment-scan` | `scan-incomplete-invoice-fragment.pdf` | INVOICE | ESCALATE | incomplete_candidate_combination | correctly did not invent evidence for missing content |
| `poor-quality-scan` | `scan-poor-quality-bol-rail.pdf` (same file OCR failed on) | BOL | **ACCEPT** | complete_candidate_combination | **the model correctly read through the blur; this is the core value case for the fallback** |
| `severely-degraded-scan` | `scan-severely-degraded-bol-rail.pdf` (visually confirmed unreadable to a human) | OTHER (forced guess) | ESCALATE | insufficient_readable_content | all 11 features correctly marked `unclear` (not `absent`); model reported the diagnostic honestly and unprompted into a match |

The `poor-quality-scan` result is the central finding of this experiment: local OCR produced unusable garbage on that exact file, but the visual model, looking at the same (blurry) image directly, read it correctly and gave accurate, specific evidence descriptions (headings, shipper/consignee/carrier names, cargo). This demonstrates the actual reason a visual fallback is worth having, rather than merely re-running the same text pipeline under a different name.

The `severely-degraded-scan` result demonstrates the fallback's own honesty boundary: on an image degraded enough that a human cannot read it either, the model did not guess a plausible-looking combination — it marked every feature `unclear` and flagged `insufficient_readable_content` unprompted (the override was not needed to reach the correct outcome here, but is kept as a defensive check, since the OCR run already showed a case where it *was* needed).

## Agreed time bounds and retries (not yet implemented)

Discussed and agreed with the user separately from the rest of this document (the first draft of this section had not actually been reviewed with her before being written down, and was reopened and confirmed on request). Not built into the experiment runner (`run_visual_classification` makes exactly one call, no retry, for feasibility testing only). Agreed for Task 6 production integration, mirroring the already-approved primary contract: 60-second request timeout, SDK automatic retries disabled, at most one retry for a technical/incomplete/refusal/schema-level failure on the single allowed visual fallback call. "One fallback per attempt" bounds the *classification* escalation, not raw HTTP retry allowance; this keeps them distinct as the plan requires. The existing 10-page/10 MB intake limit (Task 2/G0) is explicitly kept unchanged: OCR/visual processing makes each additional page more expensive (its own render, OCR pass, and possible fallback image), which argues against raising it, not for raising it; a real BOL/POD/logistics invoice is almost always 1–3 pages, so the existing cap already has headroom, and a document that needs more is more likely an unrelated multi-document bundle than a legitimate single document of these classes — that "one PDF, multiple documents" case was already scoped out during brainstorming, not something Task 5 reopens.

## Limitations

- All fixtures are synthetic (ReportLab-rendered then rasterized); no real-world scanned document (skewed, physically photographed, multi-generation photocopy) was tested. Real scans may fail in ways these degradations do not reproduce.
- Every fixture is a single page; the mixed-page and multi-page-with-partial-OCR-failure policy is a design decision, not empirically verified here.
- Small sample: 8 OCR-sourced examples, 4 visual examples. This supports feasibility and direction, not calibrated reliability or a production threshold, consistent with how Task 1/G1 was scoped.
- Only one severely-degraded example was tested; the boundary between "visual model succeeds" (poor-quality case) and "visual model honestly declines" (severely-degraded case) was not mapped in between.
- The insufficient-content override was empirically necessary for the OCR-sourced path and empirically inert (but kept) for the visual path tested so far; this is disclosed rather than smoothed over.
- No corrupted/unrenderable-page technical-failure case was exercised.

## G2 recommendation

The experiment supports the feasibility of the OCR + visual fallback direction: OCR-sourced text reuses the primary contract without modification and reproduces the correct accepted/escalated/uncertain outcome on every tested pair; the visual fallback rescues at least one concrete case where OCR failed outright, and independently demonstrates honest decline on a genuinely unreadable image. The text-sufficiency policy survived a real test that disproved its first draft, which is itself evidence the review process is doing its job rather than rubber-stamping a first guess.

This does not establish production-grade reliability, a calibrated threshold, or coverage of real-world scan artifacts — those remain explicit limitations above. Per the user's standing instruction, Task 6 (production integration) does not start automatically from this G2 write-up; it requires a separate, explicit go-ahead.
